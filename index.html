TL;DR. Are robot memory benchmarks still hard once memory can live outside the policy? We wrap a frontier multimodal LLM in a deliberately simple harness that bypasses the model's native memory (every decision is a separate, stateless API call) and lets it call only high-level skills. It nearly saturates RoboMME, its score depends on what the harness shows it, and RMBench is solved by an action log. Robot memory benchmarks need much longer horizons.

Abstract

Robot memory benchmarks were built to evaluate end-to-end policies. We ask whether they remain challenging when a general-purpose multimodal model controls the robot through high-level skills. We wrap GPT-6 Astra and Claude Opus 5.5 in a simple, training-free harness with two deliberate restrictions: every decision is a separate, stateless API call, so the model sees the past only through what the harness puts in the prompt; and the model only selects skills, so manipulation dynamics do not confound the results. On RoboMME, GPT-6 Astra succeeds in 81.3% of episodes with a text log of its past actions, and in 95.0% when it also sees images of its own past execution (Claude Opus 5.5: 76.9% and 88.8%), compared with 90.5% for humans. The gain comes mainly from three tasks whose key visual cue disappears before it is needed. On RMBench, the action log alone matches the log plus visual history (91% vs. 93%). Both benchmarks need only a few decisions per episode, so we argue that robot memory benchmarks need much longer horizons.

Two Deliberate Restrictions

We use the harness as a diagnostic instrument, not as a method to maximize success.

We bypass the model's native memory. The model keeps no chat session: every decision is a separate, stateless API call, and the harness rebuilds the request from scratch. The model therefore knows about earlier steps only what the harness puts in the prompt, and we can add or remove one memory source at a time: nothing, a structured log of past actions and their outcomes, or the log plus a visual history of the agent's own execution.

We let the model call only high-level skills. When the goal is to test memory, the agent should not be bottlenecked by the dynamics of manipulation. On RoboMME, it chooses among the benchmark's own skills, which RoboMME's planner executes. RMBench offers no skills, so the model names a skill and a pixel, and a fixed, training-free harness grounds the pixel and plans the motion. Failures then point to what the agent remembered, not to how well the arm moved.

The harness is otherwise kept minimal: no training, no retrieval, and no task-specific strategy beyond short notes on benchmark conventions. Its scores are a conservative estimate of what an agent can achieve, not the result of tuning.

What the harness remembers

Everything the model knows about the past is what the harness puts in the prompt. We compare three settings:

  • No memory: only the current image and the task.
  • Action log (text): one line per past decision, giving the skill chosen, its target pixel and the outcome, e.g. #0 press the button → done.
  • Action log + visual history (images): the same log, plus a grid of frames from the agent's own past execution (RoboMME: 24 frames sampled over the whole episode; RMBench: one frame per decision).

What Benchmarks Need Next

In both benchmarks, an episode takes only a few high-level decisions (fewer than four on RoboMME, about nine on RMBench), and the relevant evidence can simply be kept in the prompt. RoboMME remains a useful diagnostic for agent-level memory pipelines, but its success rate alone cannot be read as a measure of the native memory of the underlying model. We therefore argue that future robot memory benchmarks should include:

  1. Much longer horizons, so the full history no longer fits in context and the agent must decide what to store.
  2. Demonstrations withheld after they are first shown, so they must be remembered rather than re-read.
  3. Cues that neither the current frame nor an action log can recover, the only regime in which our ablations separate memory representations.
Limitations
  • Each RoboMME cell is run once per model on 160 of 800 test episodes; the McNemar test ignores that gains cluster within tasks.
  • RoboMME's oracle planner gives privileged execution; results concern the benchmark's memory component, not end-to-end policies.
  • RMBench's visual history holds only decision-time frames and cannot capture cues that appear during execution; the 91 vs. 93 result applies only to that form of visual memory.
  • Some RMBench task notes tell the planner what to record, which favors the action log. RMBench seeds 0–9 were also used while debugging the harness; a rerun on unseen seeds is planned.
  • We use a single planner on RMBench; a weaker open model and a full-context baseline under our harness are left for future work.
