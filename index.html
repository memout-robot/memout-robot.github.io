Abstract

Strong multimodal models can solve robot memory benchmarks when a harness supplies past information, but high success alone does not show which history matters. We compare explicit memory inputs to stateless planner calls. The model receives prior information only in the prompt, and a controller developed separately by an LLM coding agent executes the selected skill. After development on indices 0–9, we freeze prompts, task notes, skills, memory construction, and budgets, then evaluate 940 episodes on new instances of the same task families. On 160 RoboMME instances, past execution frames improve GPT-6 Astra from 76.3% to 91.9% and Claude Opus 5.5 from 69.4% to 83.8%. On RMBench, an event log with agent-written observations gives 95/100 successes, and the log plus decision-time images 97/100; on the 97 scene-matched instances, 93 and 94. These results support high performance under a frozen, task-guided harness on new instances, with substantial benefits from control-history images on RoboMME and a small observed benefit from images beyond RMBench's event log. At this scale, the full text log fits in every prompt; the experiments do not test memory selection, compression, or retrieval beyond context capacity.

Two Deliberate Restrictions

We use the harness as a diagnostic instrument, not as a method to maximize success.

We bypass the model's native memory. The model keeps no chat session: every decision is a separate, stateless API call, and the harness rebuilds the request from scratch. The model therefore knows about earlier steps only what the harness puts in the prompt, and we can add or remove one memory source at a time: nothing, a structured log of past actions and their outcomes, or the log plus a visual history of the agent's own execution.

We let the model call only high-level skills. When the goal is to test memory, the agent should not be bottlenecked by the dynamics of manipulation. On RoboMME, it chooses among the benchmark's own high-level skills, which are executed by agent-built skills: code that a coding agent wrote, tested in simulation and froze before evaluation. RMBench offers no skills, so the model names a skill and a pixel, and agent-built skills ground the pixel and plan the motion. Within each comparison the planner and the executor stay fixed, so a change in success comes from the memory supplied, not from how the arm moves.

The harness is otherwise kept simple: no training and no retrieval, only short notes about benchmark conventions, a few generic strategies and, on RMBench, what information to record.

We freeze the harness before evaluating. We developed the skills and task notes on instances 0–9, then froze the prompts, task notes, skills, memory construction and budgets, and evaluated once on new instances 10–19 of every task: 640 RoboMME and 300 RMBench episodes. No method changes were made in response to these outcomes. The task families themselves remain familiar.

What the harness remembers

Everything the model knows about the past is what the harness puts in the prompt. We compare three settings:

  • No history (RMBench only): the task, a task note and the current image; no past actions or observations.
  • Text log: one entry per past decision. On RoboMME, a structured action log with the skill, its target pixel, the result and the number of motion frames, e.g. #4 a [58,154] ongoing 86. On RMBench, an event log that also stores a one-line record written by the agent itself, which can retain visual facts, e.g. 7 place [130,173] succeeded “red uncovered first; next uncover green …”
  • Text log + visual history (images): the same log, plus a grid of past camera frames (RoboMME: 24 frames sampled over the whole episode; RMBench: one frame per decision).

With the action log alone, GPT-6 Astra solves 122 of 160 new instances (76.3%) and Claude Opus 5.5 111 (69.4%). Adding past execution frames raises these to 147 (91.9%) and 134 (83.8%). The frozen harness thus keeps high success on instances it was not developed on, without further tuning. This is not unguided performance: the full task notes remain available. Remaining failures still mix perception, task interpretation and execution, for example mistimed presses in StopCube.

Finding 3: On RoboMME, Adding Visual History Is Worth 14–16 Points

GPT-6 Astra on ButtonUnmask, development episode 0. With visual history, the agent locates the red cube from an earlier frame. Without it, the agent presses twice more and then chooses the center container. Commands and rationales are copied from the logs; b means lift a container.

Same model, same code; only the memory changes. For GPT-6 Astra, 27 new instances succeed only with past frames and 2 only without them, a net gain of 25 (15.6 points; p = 1.6×10−6). For Opus, 27 and 4, a net gain of 23 (14.4 points; p = 3.4×10−5). ButtonUnmask, ButtonUnmaskSwap and PickHighlight contribute 24 of GPT-6 Astra's 25 net additional successes and 16 of Opus's 23: initially visible cubes are covered later, or the cue appears only during a button press. An action log records the press but not the visual fact it reveals, so the benefit comes from supplying the missing observation. This does not show that images are necessary if the same facts were stored in text.

What These Scores Do and Don't Show

Memory evaluations should specify what records contain, not just whether they are text or images. RoboMME's action log omits observations, so past frames help; RMBench's event log already stores agent-written visual facts, so images add little. The different logs and sampling rules prevent a controlled cross-benchmark comparison of text versus visual memory.

These results concern a frozen, task-guided harness on new instances of familiar tasks, not an isolated measure of the model's memory capability. At the evaluated scale the full text log fits in every prompt, so the experiments do not test how systems select, compress and retrieve memory once history exceeds context capacity. Questions that longer benchmarks could answer:

  1. What does an agent choose to retain when the full history no longer fits in the prompt?
  2. Which memory representation works best under such a budget: text logs, agent-written records, images, task state or world-state graphs?
  3. Which errors come from memory, and which from planning or execution, if memory decisions are scored separately from task success?
Limitations
  • These are new instances of known task families under frozen, task-guided prompts, not tests on unseen task families or of autonomous selection of what to remember. Pretraining exposure to the benchmarks is unknown.
  • Each condition is run once; the McNemar tests do not account for gains clustering within tasks, and 10 instances per task give limited power for small effects.
  • The new RoboMME set has a different difficulty mix from the development set, so changes between them are not a pure overfitting estimate.
  • On RMBench, three requested indices resolved to different scenes across conditions; the scene-matched subset is a post-run sensitivity analysis. Action fields, memory records and record-writing guidance are not ablated separately, and the contact sheet misses cues visible only during execution.
  • Compact task-state memory, world-state graphs, full conversational context and open-weight planners are left for future comparisons.
